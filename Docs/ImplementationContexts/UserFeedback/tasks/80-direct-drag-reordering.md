## 认领的反馈条目

- 任务列表已经能直接拖拽排序，不应再要求用户先进入单独的“排序”模式；删除因此
  变得冗余的排序按钮与状态代码，并在适合的列表继续优先使用直接拖拽。

## 初始范围

- 审计 Tasks 主列表、分类/子任务菜单、Task Editor checklist 及其它已有排序入口，
  确认哪些排序按钮只是切换冗余模式，哪些仍承担 macOS 或辅助操作所需的真实能力。
- 保留现有 command/repository 排序边界与稳定身份，只调整用户触发方式；不重写
  SwiftData 排序协议，不把拖拽写入散落到 View。
- 优先使用 SwiftUI 原生 `List`、`ForEach`、`onMove`/drop destination 与平台菜单；
  不实现自定义横向手势或第三方拖拽框架。

## UI 验收清单（改动前）

- [ ] iPhone 正常字号：Tasks 页面无需先点排序按钮即可直接长按并拖动同级任务；
  移动后顺序持久化，展开/收起与导航仍正常。
- [ ] iPad 正常字号：侧边栏展开与收起状态下，拖拽命中目标清晰且不误触导航。
- [ ] macOS 正常字号：保留平台可发现、可键鼠操作的排序路径；若原生直接拖拽已完整，
  删除重复模式按钮但不删除必要的上下移动作。
- [ ] 只允许同一有效排序作用域内的移动；分类、父子层级及 Health 受保护分支规则不变。
- [ ] 删除冗余 UI 后，本地化 key、accessibility identifier、测试与文档同步收口。

## 测试优先清单

- [ ] 先用现有 command/service 行为测试锁定同级排序、跨层级拒绝与持久化结果。
- [ ] 为删除排序模式后的直接拖拽路径补 UI 自动化或稳定的交互状态断言。
- [ ] 完整测试、格式/本地化门禁、正常字号截图与 Release 全设备安装通过。

## 库策略

- 直接拖拽是 SwiftUI 原生能力，预计不新增依赖；若现有原生 API 足够，引入第三方
  reorder 库只会增加手势冲突、供应链与跨平台维护成本。
